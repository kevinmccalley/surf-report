## Shipped in this pass (PR #60 — merged + live)

Climatology transient marine-API failures no longer become sticky 404s:

- `getClimatologyData` **throws** on no-ocean-point / no-samples instead of returning `[]`
  (`unstable_cache` doesn't persist a rejection → next request retries, instead of serving
  an empty result for the full 7-day TTL).
- The page's failed-data path now renders a **500** (Google retries a 5xx) instead of
  `notFound()` (Google de-indexes a 404). `notFound()` kept only for a genuinely unknown slug.
- `generateStaticParams` returns `[]` — nothing prerendered at build time (a 24-spot slice was
  enough to rate-limit Open-Meteo in CI and fail the build). Every page renders on first
  request, then ISR + edge cache serve it.
- `maxDuration = 60` on the route; `/climatology/*` sitemap `priority` `0.7 → 0.4`.

Post-scan behaviour: a 12-wide parallel crawl produced 92 transient `500`s; a sequential
re-check recovered **90 of 92** on the next hit. The 2 that didn't → **P2** below.

## P1 — Region `spotSlugs` used place names, not break slugs — **FIXED, PR #61**

`app/lib/surf-regions.ts` listed `spotSlugs` as **place names** (`pichilemu`, `arica`,
`iquique`, `nantucket`, `saquarema`, `florianopolis`, `raglan`, `fernando-de-noronha`) —
but the catalog keys breaks by **break name** (`punta-de-lobos`, `el-gringo`, `cisco-beach`,
`manu-bay`, …). `getRegionSpots()` silently drops any slug it can't resolve, so those region
pages rendered thin (`/regions/chile` showed 1 of 4), their `ItemList` / `numberOfItems`
structured data undercounted, and the dead `/spots/<place>` + `/climatology/<place>` URLs
they referenced are the 12 entries in GSC's "Not found (404)" bucket. The spots were never
missing — the references were wrong.

**PR #61** re-points all 6 broken regions at the real break slugs (no data-file change):

| Region | was | now |
|---|---|---|
| `new-england` | `nantucket` | `cisco-beach` |
| `chile` | `pichilemu`, `arica`, `iquique` | `la-puntilla`, `el-gringo`, `el-colegio` |
| `brazil-southeast` | `saquarema` | `ita-na-beach`, `arpoador`, `prainha` |
| `brazil-south` | `florianopolis` | `praia-mole`, `joaquina` |
| `fernando-de-noronha` | `fernando-de-noronha` | `cacimba-do-padre` |
| `new-zealand` | `raglan` | `manu-bay`, `whale-bay` |

`surf-regions.test.ts` 4 failing → green; full suite 288/288.

**Deploy caveat**: `ita-na-beach`, `cacimba-do-padre`, `manu-bay`, `whale-bay` exist only in
the **dev** catalog, so PR #61 (base `dev`) clears the live GSC 404s on the next
`dev → master` sync, not before. `new-england` / `chile` / `brazil-south` would also resolve
on `master` today if a faster path is wanted.

**Still open** — make `getRegionSpots()` warn on an unresolved slug in dev so this can't
regress silently (currently it just drops them). And `/regions/fernando-de-noronha` still has
only one break in the catalog (`cacimba-do-padre`) — thin by construction until more Noronha
breaks are added.

## P1 — `nantucket` pages are indexed and earning traffic but 404

`/climatology/nantucket` — **19 impressions, 1 click** in the last 3 months (GSC Pages report) —
and `/spots/nantucket` both return **404**. Stale pages Google still ranks and sends users to.
PR #61 stops the `new-england` region *linking* them (→ `cisco-beach`), but Google keeps the
old URLs in its index until they're redirected.

**Fix**: add a `301` from `/spots/nantucket` and `/climatology/nantucket` → the `cisco-beach`
equivalents (that's the real Nantucket break — Cisco Beach, Nantucket MA). A `middleware.ts`
redirect rule, since these are the only known stale spot URLs with live impressions.

## P2 — 2 climatology pages fail permanently (not transient)

`/climatology/santa-catalina` and `/climatology/troncones-point` return `500` on every hit.
Both spots have `confidence: "provisional"` coords that round onto a grid cell Open-Meteo
has no marine data for, and the ±1.5° ring search finds nothing → `resolveOceanPoint` returns
`null` → (post-PR-#60) throw → `500` forever, where before it was a cached `404`.

| slug | name | coords | rounds to |
|---|---|---|---|
| `santa-catalina` | Santa Catalina, Panama | 7.653, -81.293 | 7.5, -81.5 |
| `troncones-point` | Troncones Point, Guerrero | 17.794, -101.748 | 17.5, -102.0 |

**Fix** — pick one:
- Nudge the two coords onto open water (both are real, exposed Pacific point breaks).
- Widen `MAX_RING` in `resolveOceanPoint` (currently 6 / ~165 km) or shrink the rounding step.
- For a genuinely no-data spot, cache a short-TTL "climatology unavailable" state instead of
  `throw` → `500` on every crawl.

## P3 — `country` field wording is inconsistent (not a bug)

Retracted as a defect. Per `docs/surf-breaks-dataset.md`, `country` is a **free-form
"locality, region" label** (historical field name) — `"North Shore, Oahu"`,
`"Santa Catalina, Panama"` are all valid. What varies is the second half: some rows end in a
country (`"…, Panama"`), some in a state/province (`"…, Guerrero"`, `"…, MA"`). Cosmetic —
worth a consistency pass during the next groundtruth **verify** run, not an SEO fix. One real
downstream effect: the climatology page renders `"…at {name}, {country}"`, so a row like
`name: "Santa Catalina"` + `country: "Santa Catalina, Panama"` reads `"…at Santa Catalina,
Santa Catalina, Panama"` — a de-dupe in that template string would tidy it.

## Nits

- `hreflang` `<link>`s render the attribute camelCased (`hrefLang`) — a React prop leaking into
  SSR output. HTML attributes are case-insensitive so Google honours it; cosmetically wrong.
- Homepage `canonical` is `https://groundswell.surf` (no trailing slash); sitemap uses
  `https://groundswell.surf/`. Google normalises, but pick one and be consistent.
